# AI 多代理并行协作开发工作流（通用版；仅系统命令与 git）

> 随 `@local/project-flow` 插件分发（技能来源 `bundled`）：`resourceBase` 即本文件所在目录，文中 `references/`、`assets/`、`scripts/` 均相对该目录解析。

> 技能版本 2.10（2026-10-28）：随 project-flow 插件分发；检查入口 `flow check`。2.9（2026-10-21）：通用精度层参考实现落地（task/doc_check/gate）。2.8（2026-10-21）：修正 B 画像写锁口径，接入清单补“已有协议”分支。2.7（2026-10-21）：新增新项目接入清单 `references/onboarding.md`。2.6（2026-10-21）：新增“项目画像”“精度层（可选）”，并将结构化任务/文档标准/门禁接线迁入通用 references。2.5（2026-10-21）：新增“项目画像”与单人降级模式；多代理纪律不变。2.4（2026-10-10）：授权模型为"反驳纠错优先、普通任务直接执行、敏感操作当次确认"；台账单写者、影响域、拒绝归档与损坏重建已纳入；CHANGELOG 碎片化建议见 §十一。**2.4 新增**：DSH 0.2.0 工具面——**自动化任务**（Host 任务板 + 会话定时，§九）与**智能体团队**（Agent Teams，§十）的工具名映射、纪律与取舍，详见 `references/agent-teams-and-tasks.md`；并新增一条**时效纪律**：文档里"某卡/某 cron 在跑"属**断言**，**点火前必须用工具核实**（本项目实测：看门狗卡与全部角色卡已归档、`armedSchedules=0` ⇒ 无人值守保护**并不存在**）。**2.3 新增**：Host 任务板卡片模式（角色卡、卡片冻结、看板绿 ≠ 交付、服务重启后的恢复纪律、权限闸门）。

以“多个 AI 子代理 + 一个协调者”为主，也支持单人/单代理降级使用；开始前先按「项目画像」选档，再决定启用哪些章节。与语言/构建体系无关。**本技能的命令只使用 shell 系统命令与 git**；随包附带的 `scripts/` 运行需要 `bash`（`doc_check.py`、`gate.py`、`task` 另需 `python3`），项目若在 CI / 非 DSH 环境使用，应把需要的脚本复制进仓库（如 `.agents/scripts/`）随版本管理，而不是依赖某个用户级目录里的副本。类型检查、lint、构建、测试、打包、安装依赖等工具链操作一律由项目技能以"命令契约"声明（见〇）。

> 本流程面向你长期维护的自己项目：默认 dev 单线开发、master 正式 / beta 预发布、提交即写 CHANGELOG。项目技能 / AGENTS.md 另有约定时，以项目为准（例如项目禁止代理写 CHANGELOG 时，不执行"提交即写 CHANGELOG"）。

## 项目画像（先选档，再决定启用范围）

| 画像 | 典型场景 | 启用 | 跳过 | 仓库产物 |
|---|---|---|---|---|
| A 单人/单代理 | 个人小项目、无 CI 或本地构建 | 硬性约束、命令契约、质量门禁、发布节奏、陷阱 | 串行令牌、波次、协调者清单、台账、心跳、任务板、Agent Teams | 代码 + 可选 AGENTS.md |
| B 单人 + 多会话/多机/CI | 有 CI、偶尔多机 | A 的全部 + 恢复协议 + 发布链 + 共享工作树时的串行令牌/轻量状态 | 波次、完整台账、心跳、任务板、Agent Teams | 代码 + CI + 可选 STATUS.md/锁文件 |
| C 多代理/多人 | 多个 AI + 协调者 | 全量 | 无 | 台账、任务书、hooks/CI 按项目 |

默认：无法判断时按 A；确认存在并行写者或跨会话交接，再升级到 C。不允许为了“看起来规范”直接上 C。

写锁看共享工作树，不看人数：单会话可省；多会话共用 `.git/index` 时必须轻量串行令牌。

## 精度层（可选，A 默认关闭，B/C 按需）

- 结构化任务：`references/structured-tasks.md` + `task-cli.md`；项目提供命令契约与 sync 映射。
- 文档标准：`references/doc-standard.md`；按骨架生成，再跑 doc check。
- 强制接线：`references/enforcement.md`；hooks → gate → CI，配置值来自项目 `gate-config`。
- 实现语言由项目决定（bash/Node/Python 均可），本层只定义行为；不强制 Python。
- 参考实现：`scripts/task`、`doc_check.py`、`gate.py`、`precision_common.py`；项目复制到 `.agents/scripts/` 即可用。
- 简单任务仍可用 `assets/task-brief-template.md`；结构化任务用于需要脚本校验、跨会话交接或多代理并行的场景。
- 新项目第一次使用：先读 `references/onboarding.md`，写命令契约、选画像，再决定是否启用精度层。

## 硬性约束（最高优先级，违反即事故）

1. **有权且必须反驳**：用户提出的内容、建议或方案，只要存在错误、不合理、不建议之处，或会累积成未来项目负担（如设计债、范围膨胀、兼容性风险），必须先指出并说明理由、影响与替代方案，不得照单执行。没有实质问题时明确说"没有异议，按你的意见执行"，不为反驳而反驳。
2. **反驳后直接推进普通任务**：反驳与建议按 [assets/advice-format.md](assets/advice-format.md) 回馈后，普通任务按已确认的任务书直接执行，不需要每条指令都等用户确认。
3. **敏感与范围外动作必须当次确认**：push、打标签、删除、改依赖、动发布分支、本地历史重写（`git reset --hard`、`rebase`、`commit --amend`）、`git clean -fd`、覆盖他人未提交改动、改 CI/发布工作流、改版本声明、`rm -rf` 类破坏性命令、改动契约外文件，执行前必须取得当次明确确认。
4. 执行中发现偏离已确认方案，先停止并回馈，再等用户确认；不得自行扩大范围。
5. 只读调研、查证、阅读代码可直接做，用于形成反驳与建议。
6. **授权分层**：任务书经用户确认后，子代理在任务书范围内向协调者负责，不再逐条找用户；范围外动作回到用户确认。子代理发现任务书或协调者指令不合理，也必须反驳协调者，不照单执行。

## 〇、项目命令契约（唯一的工具扩展点）

- 项目技能必须声明一份命令契约，协作开始前由协调者确认，任务书直接引用：
  - 验证命令：typecheck / lint / build / test / smoke（可缺省，缺省项在任务书注明"本项目无此项"）；
  - 版本声明位置清单：版本号需要同步修改的全部文件；
  - 发布脚本入口与冒烟方式、Release/CI 集成约定（如适用）；
  - 工具链禁令细节（临时执行器、依赖安装的限制等）；
  - 分支名与 CHANGELOG 策略（默认：dev / master / beta；提交即写 CHANGELOG）。
- 本技能对这些命令只有流程要求：0 错误基线、全绿才提交/push、协调者验收时全仓复跑。
- 写代理禁止使用契约之外的构建/包管理工具，禁止安装或升级任何依赖；直调工具一律用本地已安装入口，禁止包管理器的"临时执行"模式。
- 项目技能缺失或过时时，协调者先与用户拟定最小命令契约（验证命令、版本声明位置、禁止项、分支约定），写入任务书后再开工。

## 与 project-flow 插件的分工

- **台账/存储归插件**：`.dsh/flow/` 由 `@local/project-flow` 拥有——写入口是 `flow` CLI 与 `flow_*` 工具，面板是只读视图；记录字段、schema 与校验以插件 `CONTRACT.md` 为准。
- **本技能只管流程纪律**：画像、命令契约、质量门禁、提交/发布/交接纪律。**不得重定义记录字段**；需要记实验/任务/门禁时调用插件，不要在技能或项目文档里另立一套字段。
- **机械检查由插件提供**：`flow check staged|release-baseline|state|doc`（DSH 内首选入口）。同一批脚本随本技能分发在 `scripts/`，项目可在 CI / 非 DSH 环境把需要的脚本复制进 `.agents/scripts/` 直接运行。

## 一、工作模式：dev 直提（默认，不建工作分支）

> 画像：A 可直提；B 单会话直提，多会话共享工作树时用串行令牌；波次仅 C。

- **dev = 唯一开发与集成分支**：所有开发提交直接落在 dev，不新建 `branch-X` 工作分支、不做分支合并。发布分支（master 正式 / beta 预发布）与开发分开。
- **串行令牌**：同一时刻只有一个写代理在主工作区写文件；其完成通知到达、协调者验证通过后，才激活下一个写代理。只读调研可并行。
- **波次并行（演进）**：相互独立的目标可拆成多名写代理同波次并行，前提是**文件域严格互不重叠**（每份任务书写明归属文件清单），完成后协调者统一验收并 push。
- **提交归属纪律（并行波次必须）**：只 `git add` 自己清单内的文件（禁止 `git add -A`）；**commit 必带 pathspec**：`git commit -m "..." -- <自己的文件>`；提交前用 `scripts/check_staged_files.sh <允许路径...>` 或 `git diff --cached --stat` 自检；误 add 他人文件用 `git restore --staged <file>` 摘出（只动暂存区不动工作树）。
- **分支纪律（硬性）**：一切处理与变化只在 dev；master / beta 等发布分支**只通过合并（merge 或 fast-forward）接收 dev 的内容**——禁止直接提交、cherry-pick、force 更新或任何非合并操作。
- **分步提交**：每个可独立验证的步骤一次提交（`feat:`/`fix:`/`style:`/`chore:`/`refactor:`/`docs:` + 中文或英文说明）；**每个目标达成即提交**。
- 子代理不 push、不切分支、不 fetch；协调者做集成验证后统一 push。
- **卡片化并行 或 智能体团队（可选进阶）**：若部署里有 Host 任务板插件，写代理可以改成**钉住工作区/权限的卡片**（规划 / 执行 / 审核三种角色卡），由 Host 调度与结算，关掉浏览器也照跑；若部署暴露 **Agent Teams** 工具（DSH 0.2.0 起），Lead 可直接 spawn **持久队友**，在同一工作树上并行分工。两条路的硬前提**完全相同**：**文件域互斥、单一 git 写者**（Coordinator）。机制、纪律与取舍见 **§九（卡片与自动化任务）· §十（智能体团队）**。

## 二、质量门禁（每次提交/合并后必跑，命令全部来自契约）

1. **静态检查**：契约中的 typecheck + lint，**0 错误基线**。
2. **静态检查盲区扫描**：类型检查/lint 覆盖不到的构造——动态导入/反射、宏或模板生成代码、`include!` 引入的生成文件、内嵌脚本块、配置引用等——对新增/重写文件必须补扫或人工核查。
3. **资源与文案同步**：用户可见文案/资源变更必须同步全部语言或资源文件。
4. **全绿基线**：契约全部命令通过后才提交/push。

## 三、发布节奏

- 阈值：dev 自上次发布基线累积 **N 个提交**（默认 10，项目可调）后自动发布下一版；手动里程碑用 `--force` 跳过阈值。
- 发布前契约 build/test/smoke 全绿；冒烟统一用**环境变量门控探针**模式。
- 版本 bump 脚本化并同步契约列出的全部版本声明位置；预发布后缀 `.N` 从正式基线重新起算。
- 分支纪律：beta 用临时 worktree 合并接收 dev，main/master 快进；禁止直推、cherry-pick、force。
- 详细流程与停止条件：[references/release-flow.md](references/release-flow.md)

## 四、环境与协作陷阱

完整清单见 [references/collaboration-traps.md](references/collaboration-traps.md)。核心几条：

- 多行脚本/代码**先写成文件再执行**，不内联进工具参数或字符串拼接。
- 连续编辑同一文件前重读目标区段；批量/长文档改动走"整文件读 → diff → patch"；只有新建文件才整文件 write。
- grep 的结论要用第二种方法复核（编译错误、依赖树、运行时行为）。
- 子代理"已派工"不等于"已产出"：用 `git status` + 文件 mtime 核实。
- 门禁变红/合并冲突/脚本失败：保留现场，停止盲目重试，上报协调者。

## 五、协作流程清单（协调者视角）

> 画像：C 全量；A/B 跳过协调者编排，只保留派工/验收。

> 派工前先执行「硬性约束」：预研、反驳与建议回馈给用户；任务书获得确认后，范围内推进，范围外与敏感操作当次再确认。新会话、上下文压缩或中断恢复时，先执行「六、长期项目与会话连续性」的恢复协议。

1. 目标排队：串行令牌；文件域互斥时波次并行。
2. 任务书用 [assets/task-brief-template.md](assets/task-brief-template.md) 生成，必须包含：工作目录、基线确认（`git log -1 --oneline`）、恢复核对、文件归属边界、影响域/接口边界、技术要点预研结论、验证命令（契约条目）、提交规范、禁止项、停止条件。
3. 派工/恢复前做"外部世界核对"与"状态健康检查"：`git status`、当前 HEAD、台账 `COLLAB_STATE.md`、远端/CI 是否变化；未归属改动先冻结并询问用户。
4. 派工后核实产出：**队友**看 `git status` + 文件 mtime 与它的最终答复；**卡片**看**会话产出**（最后一次 `turn/end` 的 reason + 有无实质文本——**看板绿 ≠ 交付**，被中断的执行会被记成 succeeded）；长时间无改动则中断并接管（同一文件域禁止双写）。
5. 代理完成报告：改动清单、行为说明、验证摘要、提交 hash；交付验收四步：产出物存在 → 引用/接口可解析 → 事实零丢失 → 影响域接口兼容。
6. 协调者验收：复查提交内容与消息、按契约全仓复跑门禁、必要时盲区扫描；通过后统一 push。
7. 每满发布阈值执行 `scripts/release_baseline.sh '<发布提交特征>' [阈值]` 并跑发布脚本（含冒烟）。

## 六、长期项目与会话连续性

> 画像：C 必需；B 只用恢复协议 + 轻量状态/锁；A 可跳过台账，用 git log + CHANGELOG。

- **外部事实源**：每个项目维护 `COLLAB_STATE.md`（模板 [assets/collab-state.template.md](assets/collab-state.template.md)）；台账只由协调者写入，子代理用独立心跳/状态文件上报，禁止共写台账。
- **恢复协议**：先 `git log -1`、`git status`、读台账与当前任务书，再核对远端/CI；state、git、reflog 矛盾时以 git 为准并回馈差异；复跑受影响门禁。任务仍 confirmed 且范围/基线/任务书未变可续作，变化先回用户确认。
- **状态健康检查与重建**：`scripts/check_state.sh <COLLAB_STATE.md>` 检查版本、更新时间、基线漂移、容量与敏感信息；台账损坏时用 git 历史、reflog、最近任务书与提交重建，重建前不执行。
- **心跳与令牌**：写会话记录 owner/session_id/heartbeat；接管前先把 owner 置为 pending，用户确认后才正式接管，禁止双写。
- **授权与审批衰减**：任务书确认后范围内不再逐条确认；敏感操作每次重新确认；台账不存密钥。
- **上下文预算**：启动只加载台账+任务书+命令契约；references 按需读取；台账分 Active/Archive，超过 64KB 先归档。
- **恢复点与回滚**：每目标记录 last-known-good；改坏先 `git checkout` 回退再重做。
- **影响域与接口边界**：任务书同时声明文件边界和影响域/接口边界；涉及共享接口先做依赖分析，验收时复跑受影响模块门禁并检查接口兼容。
- **里程碑复盘**：每里程碑或每 N 提交写复盘结论；被反驳/拒绝的想法写入 Rejected Ideas，恢复或新任务前查重；重复陷阱合入技能。
- **跨机器/配置**：台账用仓库根相对路径；恢复时检查 git 版本、profile、模型与可用工具。
- **目标与自动续轮（goal，DSH 0.2.0 起）**：长跑目标用 `create_goal` 让会话跨自动续轮推进（非单轮任务）；`update_goal complete` 只在**真达成**、`blocked` 只在**同一阻塞连续 ≥3 轮**；**恢复/分叉后目标会被解除武装** ⇒ 用户说"继续/接着干"时先 `resume`（见 §十）。
- **入仓策略**：台账默认不入 git；入仓与否由项目契约决定，入仓时不写本地路径与敏感信息。
- 详细规则：[references/session-continuity.md](references/session-continuity.md)

## 九、Host 任务板卡片模式与自动化任务（2026-09-19 起；2026-10-10 按 DSH 0.2.0 修订）

> 画像：仅 C 且部署具备任务板时启用；A/B 跳过。

**适用**：部署里有 Host 侧任务板（DSH 为 `@linxin666/dsh-client-ui-task-board`）时，把"派子代理"升级成**派卡片**：卡片钉住**工作区 / agent 预设 / 权限**，由 Host 调度、执行与结算，**浏览器关掉也照跑**；Coordinator（台账唯一写者）仍是派单、接力、提交、汇报的唯一主体。

**工具名映射（DSH 0.2.0 实测）**：`task_board_create`（落 backlog/todo，**不执行**）→ `task_board_set_parent`（挂子任务，深度上限见板摘要 `maxSubtaskDepth`）→ `task_board_run`（**才执行**；跑父卡会**并发跑整棵子树**）→ `task_board_manage`（move / archive / restore / delete / `settle` 强收卡住的执行）；读全貌 `task_board_get` / `task_board_list`（`includeArchived` 看归档）；改卡 `task_board_update`（已执行卡的 `title`/`description`/`prompt` **冻结**，执行目标可改）；排期 `task_board_schedule`（**5 段 cron + Host 本地时区**：错过**不补跑**、卡在跑则跳过、树里有未确认权限则**拒绝并顺延**）。**会话内定时是另一套**：`schedule_*` 只给会话发提示、不干活，要"到点真的干活"必须用 `task_board_schedule`。完整清单与语义见 `references/agent-teams-and-tasks.md`。

**⚠ 时效纪律（2026-10-10 新增，本节最容易被文档骗的一条）**："某卡存在 / 某 cron 在跑 / 有看门狗兜底"**全是断言**，能否当真取决于**当前板上事实** ⇒ **派单或恢复前先 `task_board_list`（含 `includeArchived`）核实**，并读板摘要的 `armedSchedules` / `sessionDefaultPermission` / `maxSubtaskDepth`（**权限闸门只在"卡的权限 > 部署默认"时才武装**）。实测反例：某项目文档写着"看门狗卡每小时跑、永不归档"，真实状态是**看门狗与全部角色卡已归档、`schedule.enabled=false`、`armedSchedules=0`** ⇒ 无人值守保护**并不存在**，照文档行事等于把恢复押在一个不存在的东西上。

**角色分工（建议最小集）**：
- **Coordinator**：派单、接力、验收、**唯一的 git 写者**、唯一台账写者；
- **Planner**（只读权限）：产出「目标 + 可证伪 DoD + 切片与文件域 + 风险与回退 + 验证命令 + 待裁决点」；
- **Executor**（可写权限）：按任务书实现，**改动留工作树、零 git 写**；
- **Reviewer**（可写权限但**只审不改**）：独立复跑 DoD 命令、抽做变异检查、给 `pass` / `needs_revision` + findings。

**六条硬事实（2026-09-19 实测，踩过）**：
1. **卡片内容首次执行后冻结**：标题/描述/提示词只在"从未执行过"时可改（Host 硬拒 `400 task has already been executed`）；权限/工作区/模型/`reuseSession`/标签始终可改。⇒ 派单按**一事一卡**；要长期复用一张已确认的卡，就用**指针文件**（提示词固定写"读 <项目内指针文件>"，Coordinator 每次改写它）。
2. **看板绿 ≠ 交付**：结算只看 `turn/end` 的 reason 是否为 `error`，**被中断的执行（`interrupted`）会被记成成功**。复核必须看**会话产出**（有无实质 assistant 文本、最后一次 `turn/end` 的 reason），不能只看 `result`。
3. **重跑会新开一条执行记录**（旧记录的结果永久保留，列表顺序不代表新旧）⇒ 判"最新一次执行"要按开始时间排序。
4. **服务重启后的恢复**：卡片台账（定义/排期/执行记录）持久化并对账；**半途未记下会话 id 的启动会被结算成"取消"且不重发**；**cron 错过的触发点跳过、不补跑**；会话本身持久化，卡片开 `reuseSession` 后重跑**接着原会话历史继续**（会话不存在或非空闲时自动新开，不阻塞调度）；**协调者自己的后台任务随 Host 一起消失且不通知** ⇒ 恢复只能靠 Host 侧机制（看门狗卡 + Host 自启）。
5. **看门狗卡**：用**只读权限**的定时卡判"运行中但会话最后事件太久没动"或"成功但被中断 / 无实质产出"⇒ 重新触发；**同一张卡 1 小时内 ≥2 次执行只报告不重跑**（防死循环）。前提是 Host 自身能在重启后起来（systemd user service / 启动器自启），否则没有任何调度。
6. **权限闸门是防升级设计**：有效权限高于部署默认值时，卡片**首次运行需要人确认一次**，改权限或交接包会**重新武装**闸门；卡片创建卡片也绕不过（新卡仍未确认）。别用"卡自己建卡"来免确认。

**并行度（波次派单）**：卡片默认**不排队**（可以同时跑）；所谓"串行"通常来自协调者的策略与三类真限制——① 同一文件域不能双写（含「一张卡 `git mv`、另一张改同一文件」）；② 共享构建产物目录（并发构建检测会直接拒绝）；③ 依赖链与单一提交写者。做法：派单前写**域矩阵**，同波内写域两两不相交、只读卡可任意同波；**一波只允许一张卡跑全量门禁**，其余跑定向命令，全量门禁在波次收口跑一次；波次规模 2–3 张；复核 A 与下一波的规划 B 可重叠；**大规模只读扇出**用并行子代理/工作流工具，不要把看板当批处理队列使。

**分支纪律**：卡片会话**看不到你的对话上下文** ⇒ 派单必须自带任务书路径、允许的文件域、交付格式、零 git 写；**同一时刻同一文件域只允许一张卡在跑**（Coordinator 排队）；提交、台账、CHANGELOG 始终归 Coordinator。

## 十、智能体团队（Agent Teams；DSH 0.2.0 新增，2026-10-10 实测）

> 画像：仅 C 且本次会话确需多路并行时启用；A/B 跳过。

**工具**：`spawn_teammate`（Lead 专用；`context` = `fresh` 无历史 / `fork` 继承**已完成**轮次）· `send_message`（durable，**唯一能唤醒 inactive 队友**的手段，也是派新活的方式）· `wait_agent`（只观察**调用之后**的状态/邮箱/任务变化，**从不唤醒**任何成员；无人在跑时立即 `noProgress`）· `list_agents`（`inactive` = 此刻没在跑，**不代表失败或完成**；`provisioning` / `failed` 才是创建态）· `interrupt_agent`（Lead 专用，**保留 pending inbox**）· `team_task_create` / `get` / `list` / `update`（共享任务板；`update` 用 `expected_revision` 做 **CAS**：claim → 干活 → complete）。

**纪律（与卡片模式同源；差异处已标注）**：
1. **同一份工作树**：队友与 Lead 共用一个文件系统，改动**立即互相可见** ⇒ 写域必须**先声明再动手**（`team_task_create` 的 `write_scopes`）。**重叠只是提醒，不是锁**——没人会替你挡住双写。
2. **只读可任意并行，写入按域切分**：一波 2–3 个写队友；**大规模只读扇出**用 `workflow` 或并行子代理，别用队友硬顶。
3. **派工自带上下文**：队友**看不到 Lead 的对话** ⇒ 提示词必须含任务书路径、允许写域、交付格式、**零 git 写**、停止条件。
4. **readiness 不会自动开跑 owner**：任务存在 ≠ 有人在做；要让队友动起来必须 `send_message`，`wait_agent` 只会等。
5. **Lead 必须等必需队友收口再给最终答复**；队友的"已完成"是**声明**，交付按**产出物**验收（`git status` + mtime + 复跑门禁），与卡片共用同一套四步验收。
6. **提交、台账、CHANGELOG 始终归 Lead/Coordinator**：队友与卡片一律零 git 写。
7. **只在用户明确要求时组建团队**：团队适合**本次会话内**的多路并行且需要来回对话；跨会话 / 无人值守 / 要钉工作区与权限仍走卡片（§九）。

## 十一、CHANGELOG 建议形态：碎片 → 生成 → 同源检查（2026-09-19 建议）

> 画像：建议项；A/B 可继续用单文件 CHANGELOG。

手写单文件 CHANGELOG 有三个结构性毛病：**并行硬串行点**（每个提交都要改同一个文件）、**无长度预算**（单条动辄数千字符，一个版本段可达十几万字符）、**无校验**（格式/是否面向用户全靠自觉，发布说明得手抄）。建议改成：

1. **碎片**：每次提交写一个文件（如 `.changelog/unreleased/<时间>-<slug>.md`），带 front-matter：`type` / `scope` / `userFacing` / `summary`（一句话，给长度上限制）；正文可选并同样限额。
2. **生成**：`CHANGELOG.md` 变成**生成物**——构建脚本把碎片渲染进 `[Unreleased]` 的**带标记生成区**（`<!-- generated:start/end -->`），标记区外一个字节都不许动（幂等、可 diff）。
3. **同源检查**：与"生成物必须与源同源"的检查同一套路（渲染结果 ≠ 磁盘内容 ⇒ 退出码非 0），并入质量门禁与 CI ⇒ 从此没人手写、也就没有"插入锚点写错吞掉标题行"这类事故。
4. **闸门迁移**：提交前检查从"必须包含 CHANGELOG.md"改成"**必须带一个新碎片**"（无用户可见变更时显式声明豁免）。
5. **历史拆分**：主文件只留 `[Unreleased]` + 最新一版，更老版本段逐字搬进 `CHANGELOG-history.md`（**历史不改写**）。
6. **附带收益**：`userFacing` + `summary` 让**发布说明草稿可自动生成**（发布页要的是用户向摘要，不是工程细节）。
